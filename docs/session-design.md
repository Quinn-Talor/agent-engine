# 会话方案（多轮对话）

> 状态：已实现（S0–S3），评审四轮（第四轮按"不考虑向后兼容"复审并修复，见 `vibe/features/f26-session-review/`）。要点已并入 `docs/agent-engine-design.md`（§0.1、§3.5、§3.15、§6.2、§7 的 I7 与 I17、§8.5、§9.3、§11）。

## 1. 背景

引擎现在只认识"一次运行"。多轮对话由应用自己接：读上一轮的运行日志，取出 blob，拼成下一轮任务的 `history`。问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 每个应用自己推导 history | 要懂成对规则、日志结构和 blob；容易拼错（只带上一轮的运行记录、不带上一轮的 history，第三轮起丢掉第一轮） |
| 2 | 压缩只在一次运行内增量推进 | 每轮都从完整 history 重新压缩：成本随轮次上涨，摘要每轮不同，前缀缓存打不中 |
| 3 | 轮与轮的关系没有记录 | 只能按 `subject` 查出运行；接续、分叉都没有记录，审计和重放还原不出模型当时看到的前文 |
| 4 | 同一会话可以同时跑两轮 | 两轮都基于旧的 history，结果互相覆盖，引擎不知道 |

另有一个与会话无关、会话会放大的问题：上下文超限检查用的是 `估算 >= 模型窗口`，没有给输出留空间；接近上限时请求能发出去，却被厂商拒绝或输出被截断。

## 2. 边界

| | 产品层 | 上下文层 |
|---|---|---|
| 包括 | 会话 id 怎么来、谁能访问、会话列表与搜索、界面停在哪个分支、删除的时机、跨会话的长期记忆 | 同一会话一次只跑一轮、轮与轮的接续与分叉、下一轮带入的窗口、跨轮压缩、副作用台账、按会话保留与删除 |
| 归谁 | 应用（配置与选择归应用） | 引擎（承载与使用归引擎，P6） |
| 理由 | 每个产品都不一样 | 关系到不变量：成对（I2）、副作用不重做（I15）、模型调用计入预算（I8）、可重放 |

设计 §0.1 的"引擎不负责会话管理"改为"会话的产品层归应用；会话的上下文归引擎"。不带会话的调用与现在完全一样，应用仍可以自己给 `task.history`。

## 3. 会话日志与窗口

| | 会话日志 | 窗口 |
|---|---|---|
| 是什么 | 发生过的全部事实 | 模型在某一轮开始时读到的前文 |
| 范围 | 整个会话，包括所有分支 | 某个分支上的一轮 |
| 大小 | 只增不减 | 有上限（§7 的各条线） |
| 内容 | 每轮的运行日志：输入、模型回复、工具的原始结果与展示结果、压缩记录、交付、结局 | 摘要 + 最近的原文 + 结局说明；另带副作用台账 |
| 怎么变 | 只追加 | 每轮一份，写入后不再改；下一轮算出新的一份 |
| 谁读 | 引擎、应用、审计、重放 | 模型 |
| 丢了怎么办 | 不能丢，是事实来源 | 能从日志重新算出来 |

三条关系：

1. **窗口由日志算出来，反过来不成立。** 压缩只决定模型这次看什么，不删改日志里的任何一条。
2. **窗口本身也记进日志。** 每一轮带入的窗口冻结在这一轮的 `run_started` 里（消息在 `task.content`，元数据在 `session.window`），每一步的压缩决定记在 `context_built.compaction` 里。日志里因此有两类内容：发生了什么，以及模型当时看到了什么。窗口不是缓存：模型的每个决定都基于它做出，所以它要留证。
3. **窗口丢掉的，日志里都还在。** 会话按整体保留和删除（§13），不会只剩半条链。

```
第 N 轮的运行日志（会话日志的一段）
  run_started{冻结的 W_N} → context_built{压缩决定} → 回复、工具结果… → run_ended
        ▲ 受理时写入                                      │
        │                                                 ▼ carry：确定性，不调用模型
       W_N ─────────────────────────────────────────▶ W_{N+1} → 写进第 N+1 轮的 run_started
```

## 4. 接口

```ts
// 接着会话里最新的一轮
environment.start(agent, task, { session: 'case-1024' })

// 接在指定的一轮之后（编辑旧消息、重新生成、切回旧分支）：形成分叉
environment.start(agent, task, { session: 'case-1024', continues: runId })

// 从头开始的分叉（编辑第 1 轮）
environment.start(agent, task, { session: 'case-1024', continues: null })

archive.query({ session: 'case-1024' })       // 会话的轮（带 turn、continues）与没开始的尝试；子运行按 rootRunId 查
engine.previewWindow({ session: 'case-1024' }) // 下一轮会带入的窗口，不调用模型；有一轮正在运行时 session_busy
engine.deleteSession('case-1024')             // 整个会话（含子运行与固定的运行）一起删除
```

- 带 `session` 时任务不能再给非空的 `history`，否则受理失败（`invalid_task`）：一个会话的前文只有一个来源。
- `continues` 必须是同一会话里的一轮，否则受理失败（`invalid_task`）。
- `task.subject` 缺省取会话 id，按主题查运行时一个会话就是一个主题。

## 5. 一轮的流程

```
受理
  1. 核对 Agent、任务（带 session 不能有 history）
  2. 等启动时的中断补齐完成；本引擎里同一会话有运行中的轮 → 受理失败 session_busy（可重试）
  3. 推导窗口：carry(接续点的窗口与日志)（§6）
     台账：序号最大那一轮的台账 + 那一轮及其子运行的副作用（§9）；本轮序号 = 最大序号 + 1
  4. 确定模型（窗口里的图片也参与视觉要求的核对）
准备（能力拿到的 history 就是窗口）
run_started：冻结窗口、序号、接续点
步循环
  每一步组装：记忆给出压缩决定 → 引擎渲染视图（§8）→ 还超限时 C 裁剪 → I7 检查
结束：释放本轮
```

**执行时模型读到的前文只有窗口。** 组装用的 history 就是冻结的 W_N；记忆只能声明"前 k 条换成这段摘要"，视图由引擎渲染。模型看到的前文只可能是 W_N，或者 W_N 套上一次已声明的压缩。会话日志的其余部分只在推导和检查时读取。

## 6. 窗口怎么递推

`W_{N+1} = carry(W_N, 第 N 轮日志)`，N 是接续点。确定性的纯函数，不调用模型：

1. 取 W_N 的消息 H、第 N 轮的输入 I、第 N 轮的运行记录 T（按来源标记）。只读到第 N 轮日志的某一条为止，并把这条的序号记进新窗口（`continues.seq`）：之后再追加到第 N 轮的事件（例如重启后的中断补齐）不改变已经推导出的窗口，I17 也按这个序号复核。
2. 套上第 N 轮最后一次**已提交**的 `context_built.compaction`：前 `upTo` 条（H 与 T 连起来编号，I 不在其中）换成摘要消息。每一步的 `context_built` 都带着当时生效的压缩，没有这个字段就是没有压缩；坐标就是当时记忆用的坐标。H 的第一条可能是带入的摘要。
3. 拼成 `渲染后的 H + I + 渲染后的 T`——与组装视图里前文、任务输入、运行记录的顺序相同。
4. 只带对话本身：
   - 保留模型回复、工具调用与结果、委托人引导、交付退回的提示（`delivery`，说明为什么有第二版答复）；
   - 去掉其余监督提示（步数、预算、纠偏之类只管本轮的话）和须知的动态内容（`hook`：每一轮重新生成，带过去会一轮多一份）；
   - 模型回复里的推理内容原样保留，与一次运行内的处理相同：开启 thinking 的厂商续做工具调用时要求最后一条 assistant 消息带着签名；换了厂商、不能回传的，由适配器的 `dropReasoningHistory` 去掉。
5. 成对兜底：工具调用缺结果时（只在存储失败的路径上出现）补一条 `TOOL_MISSING_RESULT`，不带着坏窗口跑，也不让会话卡死。
6. 在末尾补上这一轮的结局（§11），再补上本轮最后一次组装之后才收到的委托人引导（一条 user 消息）。
7. 记下每一轮在窗口里的起点（`turnStarts`）、当前摘要和 carry 的版本。

压缩覆盖到第 N 轮运行记录时，I 放在摘要之后，摘要里可能含有 I 之后的步骤——与现在一次运行内压缩后的布局相同。

接续点的压缩若在提交 `context_built` 之前进程中断，视为没有发生：carry 只认已提交的记录。

## 7. 窗口大小

每一轮按本轮的实际模型计算：模型、可见工具、本轮输入每轮都可能不同。

| 量 | 算法 |
|---|---|
| 输出预留 | 模型声明的输出上限，最多取窗口的一半；记入 `run_started.outputReserve`，并作为主调用和兜底调用的 `maxOutputTokens` |
| 输入上限 | 模型窗口 − 输出预留（I7 按它判超限；记忆的各条线也按它算） |
| 固定占用 | 须知 + 指令 + 能力说明 + 工具定义 + 本轮输入 + 尾部（含副作用台账） |
| 可用空间 | 输入上限 − 固定占用：留给前文和本轮运行记录 |

| 线 | 默认 | 作用 |
|---|---|---|
| 轮开始线 `turnStart` | 50% | 第 1 步组装时，带入的前文超过它就压缩，给本轮的工具输出留出一半 |
| 轮中触发线 `trigger` | 80% | 每一步组装时，前文 + 运行记录超过它就压缩 |
| 保留线 `keepRatio` | 10% | 压缩后保留的最近原文最多这么多（`keepRecentTokens` 给出绝对值时以它为准） |
| 摘要上限 `summaryRatio` | 10% | 摘要请求的 `maxOutputTokens`，至少 256，不超过摘要模型的输出上限，也不超过它的窗口减去输入预算（输入最多占窗口的一半）；提示词里写明长度 |
| 成本上限 `maxHistoryTokens` | 不设 | 窗口很大的模型也不让带入的前文超过它：给出时可用空间按 min(可用空间, 成本上限 ÷ 轮开始线) 计算，各条线随之缩小，压缩之后也留在它以内 |

压缩后前文约为"摘要 + 保留的原文"，不超过可用空间的 20%，离轮中触发线足够远。

| 模型 | 输入上限 | 可用空间 | 轮开始线 | 轮中触发线 | 保留线 | 摘要上限 |
|---|---|---|---|---|---|---|
| 窗口 128k，输出 8k，固定占用 10k | 120k | 110k | 55k | 88k | 11k | 11k |
| 窗口 32k，输出 8k，固定占用 6k | 24k | 18k | 9k | 14.4k | 1.8k | 1.8k |

**保留线的唯一例外**：本轮最近一组工具调用与结果整组保留（`anchors` 默认 1，只在本轮的运行记录里数），即使超过保留线——模型下一步要基于它行动。原来的默认 4 组、并且跨到以前各轮去数，工具结果大时会顶破保留线，轮开始时更会让压缩几乎不起作用。

**超限检查对输入上限**（I7）：估算达到输入上限就不调用模型。`run_started` 必须记下 `contextLimit` 与 `outputReserve`。

## 8. 压缩时机与切点

| 时机 | 条件 | 做什么 | 调用模型 |
|---|---|---|---|
| A 轮开始 | 第 1 步，带入的前文超过轮开始线或成本上限 | 切下前文较早的部分并入摘要 | 是，计入本轮预算 |
| B 轮中 | 每一步，前文 + 运行记录超过轮中触发线 | 增量压缩（现有机制，改为按可用空间计算） | 是，计入本轮预算 |
| C 超限裁剪 | 压缩之后估算仍达到输入上限（压缩失败、冷却中或预算不够） | 引擎确定性地丢掉前文里最早的整轮，必要时丢到只剩摘要：摘要不变，末尾加一行"更早的 N 轮对话已省略" | 否 |

- A、B 由记忆组件做（`compactingMemory`）；C 由引擎做，只对带轮边界的会话窗口生效，从不丢本轮的运行记录。C 只记录放得下的裁剪：丢到只剩摘要仍超限时不写进日志，按现在的规则以 `context_overflow` 结束，下一轮的窗口仍含更早的各轮。
- C 也是一次"压缩"，只是摘要文本由引擎生成，所以 carry 不需要为它特判；下一步记忆的压缩照常进行。
- 记忆出错、超时、返回值不合格或切点拆开成对时，沿用上一步生效的压缩：压缩一旦声明，记忆失败不能让它退回，否则 C 会把只存在于摘要里的更早各轮永久丢掉。第 1 步没有上一步时不压缩。
- `compactingMemory` 同一时刻只做一次摘要：引擎等不及（记忆超时）进入下一步时，不从旧的位置并行发起第二次。
- 摘要被截断（`finishReason` 为 `length`）时要求压到一半长度重试一次，仍截断才算压缩失败：累积的摘要接近上限时不会每次都失败、永远停在 C。压缩失败 3 次后冷却 60 秒（现有规则），冷却期间只能走 C；冷却提示放在尾部，不进运行记录，不会被带到下一轮。
- 不做轮结束后的预先压缩：用户不再继续时这次调用白花。

**切点**：

| 部分 | 规则 |
|---|---|
| 以前各轮 | 切点落在前文里时，顺延到下一轮的起点：被切的轮整轮并入摘要 |
| 最近的一轮本身超过保留线 | 在这一轮内部按成对边界切，保住它的结尾（通常是最终答复）；单条消息就超过保留线时整轮并入摘要（过长的记录在摘要请求里截断） |
| 本轮运行记录 | 成对边界；保住本轮最近一组工具交换 |
| 本轮输入 | 不切（I3） |

上一轮的输入不单独钉住：它所在的轮整体超过保留线时随那一轮并入摘要（摘要的"意图"字段保留它）。委托人最近说的话——本轮输入——永远是原文。

## 9. 永远不压缩的内容

| 内容 | 怎么保证 |
|---|---|
| 本轮输入、须知、指令、能力说明 | 固定布局与前缀复核（I3） |
| 副作用台账 | 引擎确定性生成，放在尾部，不交给摘要模型（I15 跨轮） |
| 会话级业务事实 | 应用放在 `task.context`、须知或能力说明里，不放进前文 |

**副作用台账**：本会话已执行和可能已执行的副作用，每条记"第几轮、工具、输入（前 200 字）、状态"。

- 沿序号递推，不沿接续点：新一轮的台账 = 序号最大那一轮的台账 + 那一轮的副作用。同一会话串行，序号最大的轮一定已经结束；分支 B 能看到分支 A 已经发出的律师函。和对话一样只读到那一轮的某一条事件为止，序号记进 `window.ledgerFrom`。
- 有副作用的调用没有结果（存储失败、进程中断）时记为可能已执行，与 carry 补上的 `TOOL_MISSING_RESULT` 一致。
- 子运行的副作用也进台账（按 `rootRunId` 找到），代替发起它们的那次委托调用。
- 上限 50 条：可能已执行的全部保留，已执行的保留最近的，省略的记条数。

## 10. 压缩用哪个模型

**默认用本轮的模型**（现在的缺省行为）：窗口一定够；摘要有损且跨轮累积，用主模型损失最小；不需要额外配置；token 估算按它校准。

`compactingMemory({ model })` 仍可指定别的模型。摘要请求的分块按两个模型中较小的窗口计算，摘要上限不超过指定模型的输出上限：组件经 `ctx.modelLimits(ref)` 取得它们。指定模型的调用按本轮模型的价格计入费用，这是现有的计费方式，方案不改。

## 11. 结局

每一轮在窗口里以结局收尾，下一轮知道上一轮最后对委托人说了什么：

| 接续点的结局 | 运行记录里已有 | carry 补上 |
|---|---|---|
| `completed` | 最终答复或 `submit` 调用 | — |
| `awaiting_input` | `ask_user` / `propose` 调用与确认；本轮输入就是委托人的回答 | — |
| `finalized` | 最后一步 | 兜底交付的文字（一条 assistant 消息），加一行结局说明 |
| `stopped`、`failed`、`aborted`（含进程中断补齐的运行） | 到中断为止的记录 | 一行结局说明（状态、code、原因）；可能已执行的副作用在台账里 |
| 没有写进 `run_ended`（存储失败） | 到中断为止的记录 | 一行"结局没有记录" |

没开始的运行（受理失败、被须知拦下）没有 `run_started`，不占序号，不能当接续点；缺省接续点会跳过它们。

## 12. 并发与分叉

- **部署前提**：一个档案只由一个引擎实例写。现在的中断补齐已经这样假设：启动时把档案里所有没结束的运行补记为中断。多实例部署时每个实例用自己的档案，按会话把请求路由到同一个实例（会话亲和）；多个实例共用一个档案时，重启的实例会把别的实例正在跑的轮补记为中断。
- **串行**：同一会话同一时刻只有一轮在跑，包括不同分支——它们共用同一个外部世界。第二轮到来时受理失败 `session_busy`（可重试），不排队。受理前先等启动时的中断补齐完成。
- **运行中的追加**：委托人在本轮运行时说的话用 `run.steer(text)` 并入本轮；本轮最后一步之后才到的引导由 carry 带进下一轮（§6）。运行已经结束时 `steer` 返回 `false`，应用改为开新的一轮。
- **分叉**：会话树就是 `continues` 连出来的树，分叉就是 `continues` 指向的不是最新一轮。

| 操作 | `continues` | 带入的窗口 |
|---|---|---|
| 接着问 | 不传（序号最大的一轮） | carry(最新一轮) |
| 重新生成第 k 轮 | 第 k 轮的 `continues`，输入同第 k 轮 | 与第 k 轮带入的消息相同（同一 carry 版本下、且接续点之后没有追加事件时逐字节相同；台账跟着最新的轮走，可能不同） |
| 编辑第 k 轮的问题 | 第 k 轮的 `continues`，新输入 | 同上 |
| 从第 k 轮之后另起 | 第 k 轮 | carry(第 k 轮) |
| 编辑第 1 轮 | `null` | 空 |
| 切回旧分支继续 | 旧分支的末轮（必须显式传） | carry(那一轮) |

- 对话按分支走：窗口只沿 `continues` 递推，另一分支的原文和摘要都进不来。
- 外部世界按会话走：台账沿序号递推（§9），串行不分分支。
- 界面停在哪个分支属于产品层：切回旧分支后继续，应用必须显式传 `continues`。

**子运行**：只有根运行是"轮"，取序号、参与串行和接续；子运行不带会话，按 `rootRunId` 归到它的轮。

## 13. 存储、保留与删除

- **存储**：窗口的消息照旧存在 `run_started.task.content`（`{ input, history }`）里，元数据（序号、接续点、轮起点、摘要、台账、carry 版本）在 `run_started.session`。窗口有上限，所以每轮的存储量与窗口大小相关，与会话长度无关；回归重放照旧从 `task.content` 取语料。
- **保留**：会话按整体过期——会话里的每个运行（含子运行）都按各自执行环境的天数过期了，整个会话才一起清理；有固定的运行时整个会话保留。不会出现只剩半条链的情况；整个会话过期之后，同一会话 id 再开始时从第 1 轮、空窗口重新开始。清理恰好与这个会话的新一轮同时发生时，新一轮照常使用已推导出的窗口；`sessionLogIssues` 跳过接续点或台账来源已被清理的轮、以及 carry 版本不同的轮，不报为违反。
- **删除**：`engine.deleteSession(id)` 先占住会话（有运行中或正在受理的轮时 `session_busy`），再调用 `archive.deleteSession(id)` 删除会话的全部运行、它们的子运行和固定的运行（显式删除优先于固定）；档案里有没结束的运行时返回 `session_open`。随后清除不再被其他运行引用的 blob：在会话结束之后没有被再次写入过的 blob 不受宽限期保护。残余风险：别的运行恰好在会话结束前写入了逐字节相同的 blob、又在删除之后才写入引用它的事件时，这个引用会失效。后面各轮的窗口可能含有前面各轮的内容，所以不提供只删一轮。
- **档案文件**：SQLite 档案的表结构版本不同时拒绝打开，不做迁移，删除后重建。

## 15. 怎么保证窗口就是窗口

1. **只有一个渲染函数**：`renderView(前文, 运行记录, 压缩声明)`。组装、carry、`previewWindow` 都调它，结果天然一致。
2. **记忆只给决定**：`recall` 返回 `{ compaction?: { upTo, summary }, notice? }`，不返回消息列表；记忆拿到的是前文与运行记录的深拷贝，改了也不影响运行。引擎检查切点不拆开成对，不合格、出错或超时时沿用上一步生效的压缩（§8）。
3. **冻结**：每轮的窗口在受理时算出、写进 `run_started`，之后执行、重放、审计都读它，不再推导。
4. **新增不变量 I17**：同一 carry 版本下，每一轮冻结的窗口等于 carry(接续点的窗口与日志，读到记下的序号为止)；台账等于上一序号轮的台账加它及其子运行的副作用（同样读到记下的序号；子运行总在根运行结束之前结束，整份读取）。子运行按开始时间、再按 runId 排序，推导结果与档案的查询顺序无关。窗口的消息用规范 JSON 存储并用 `parseCanonical` 读回，附件的字节跨轮不变。`testing` 提供 `sessionLogIssues(archive, session)` 逐轮检查，会话测试和示例都跑它。
5. **成对兜底**：carry 补齐缺结果的调用（§6 第 5 步），推导出的窗口总是成对的。

每一步先写测试，重点覆盖：

- 属性测试：任意轮数、任意压缩位置与分叉下，成对不被破坏，I17 成立，跨分支的副作用都在台账里；

## 18. 风险

| 风险 | 应对 |
|---|---|
| 摘要错误跨轮累积 | 摘要字段固定，要求保留数字和来源；出错后可以从更早的一轮分叉；离线重建另做（§19） |
| 不兼容旧日志、旧档案文件、旧的自定义记忆 | 包未发布，不做迁移；旧档案文件删除后重建 |
| 多实例写同一档案 | 部署前提是一个档案一个写者；多实例各用自己的档案，按会话亲和路由 |

## 19. 评审后不做的事

| 原设想 | 不做的理由 |
|---|---|
| 全局的"会话消息位置"与"窗口状态" | 本轮输入不在记忆的坐标里、C 会留下洞，按位置推导会丢消息或把丢掉的轮带回来；逐轮递推没有这些问题 |
| 在运行里重建窗口（`rebuildWindow`） | 要把整条会话原文冻结进一轮、在一次记忆调用的时限内分块压完，长会话必然超时，结果比原窗口更差；需要时另做离线重建任务 |
| 同进程排队 | 运行中的追加用 `steer` |
| 兼容旧日志与旧档案（可选字段的兜底、SQLite 迁移、回归重放的任务内容覆盖） | 包未发布；只保留一种写法 |
| 跨进程的唯一约束、租约 | 现在的中断补齐已假设一个档案一个写者；唯一约束在这个前提下多余，跨进程协调需要租约，另做 |
| carry 去掉推理内容 | 开启 thinking 的厂商续做工具调用时要求带着签名；能不能回传按厂商决定，适配器已有 `dropReasoningHistory` |
| 中断的轮附上 `retrospect.brief` | 窗口里已有那一轮的原文，可能已执行的副作用在台账里，结局说明给出状态 |
| 钉住上一轮的输入 | 需要在前文中间留洞，压缩就不再是前缀；本轮输入永远是原文 |
| 指定的压缩模型不可用时改用本轮模型 | 失败会进入冷却和 C，不需要第二条兜底 |
| 分叉时继承分叉点之后的摘要 | carry 只沿接续点递推，看不到它们 |
