# 守卫机制方案（观察 → 反思 → 裁决）

> 状态：已实现（F18）。与本文的差异：有副作用的操作以相同输入第 2 次成功后才封住（本文 §3.2 守卫 4 写的是第 1 次），避免没有声明副作用的工具重复读取时被误封；"告知过"以告知真正进了纠偏消息为准；单条发现上限 400 字；时间压力按收尾预留之前的可用时长计；顾问的调用上限按运行记、不封意图工具与轮询类工具。§7 的探索实验尚未进行。
> 依据：[`docs/agent-engine-design.md`](agent-engine-design.md)（v1.2）§3.8–3.10、§9.4–9.7、§10；参考 Talor `src/main/loop/`、`src/main/tools/` 与 `docs/engineering/standards.md` J-SHOULD-2。
> 范围：替换设计 §10 的标准监督（指标 + 阶梯纠偏 + 诊断器），以及 §3.9 反思、§3.10 判定的意见来源。其他环节已有的防护不改。

---

## 0. 原则与范围

- **机制**：观察 → 反思 → 裁决。实现上分四段：事实（核心计算）→ 守卫（负责观察和反思）→ 裁决（核心）→ 交付验收。
- **原则**：在能可靠交付的前提下，少就是多。每个守卫都必须对应到一条交付保证：
  - G1 一定会结束
  - G2 终止前先告知
  - G3 结束时有交付
  - G4 不接受假完成
  - G5 可追溯
- **参考 Talor**：借鉴它的经验和教训，不照搬它的代码结构。
- **本方案的范围**：步级守卫、纠偏、和交付环节的衔接。其他环节已有的防护不改，只在第 2 节的全景里列出来。

**结论**：大部分 Talor 机制在 agent-engine 里已经有了，只是分布在别的环节，比如交付验收、工具流水线、工具呈现。步级守卫真正缺的是三项：

- **静默推进**（来自 tool-only-loop）；
- **防重复副作用**：Talor 没有这项，它是 agent-engine 不变量 I15 的要求（有副作用的调用不能自动重做）；
- **顾问**：吸收 periodic 和 escalation，降为可选。

## 2. 守卫体系全景（按环节）

| 环节 | 防护 | 由谁负责 |
|---|---|---|
| 受理 | 校验 Agent 和任务；模型是否满足要求；准入排队 | 核心 |
| 准备 | 排除不可用的能力；委托人联系不上时排除 ask_user、propose | 核心 |
| ① 组装 | 上下文超限就停止；复核调用和结果成对；记忆压缩（任务输入不压缩）；工具呈现 | 核心 + 组件 |
| ② 推理 | 并发上限、熔断、超时、重试 | 模型库 |
| ③ 行动 | 查找、封路拦截、参数诊断、工具自校验、权限与审批、熔断、超时、规整输出 | 工具流水线 |
| **④⑤⑥ 评估** | **步级守卫 + 裁决（本方案的重点）** | 守卫 + 核心 |
| 交付 | 输出校验；验收（completionReview、groundingCheck）；兜底交付 + sanitize | 交付物 + 执行环境 |
| 结束 | 不变量自检；补齐进程中断的运行 | 核心 |

## 3. 步级守卫

### 3.1 契约

```ts
interface Guard extends Component {                 // id、version、config
  onError?: 'ignore' | 'stop'                       // 出错时怎么办，默认 'ignore'
  start(run: RunInfo, ctx: ComponentCtx): {
    // 观察：读本步事实，更新自己记的账
    // 反思：给出意见；没有意见就返回 undefined
    check(facts: StepFacts): GuardOpinion | undefined | Promise<GuardOpinion | undefined>
  }
}

type GuardOpinion = { detail?: string } & (
  | { warn: { problem: string; suggest?: string; block?: CallBlock[] } }   // 告知，可以顺带封住调用
  | { awaitInput: { code: string } }                                       // 需要委托人回复
  | { end: { as: 'finalize' | 'stop'; code: string } }                     // 终止
)

type CallBlock = { tool: string; inputHash: string; code: string; reason: string }
```

- 账记在守卫实例自己身上，不写日志。日志里只写守卫给出的意见和 `detail`，用来解释为什么这样裁决。
- 只用一个 `check`，不拆成观察和反思两个方法：每一步都会执行所有守卫，不会出现排在后面的守卫轮不到、计数漏步的问题。
- 守卫要能复现：给它同样的事实序列，就得到同样的意见。需要外部数据时通过 `ctx.record` 获取，回归重放时从日志读回。

`StepFacts` 有三处调整：每个工具调用新增 `errorClass`（错误类别，见下表）；`pressure` 新增 `tokens`；`pressure` 去掉 `supervision`。

**错误分类**（核心维护一张表）：

| 类别 | 错误码 | 含义 |
|---|---|---|
| 确定性 | `INVALID_INPUT`、`PERMISSION_DENIED`、`USER_DENIED`、`SPAWN_*` | 同样的输入再调一次，结果必然相同 |
| 瞬时 | `TOOL_TIMEOUT`、`TOOL_UNAVAILABLE`、`TOOL_EXCEPTION`、`SUBAGENT_*` 及其他 | 再试一次可能成功 |

工具可以通过 `semantics.deterministicCodes` 和 `semantics.transientCodes` 声明自己定义的错误码属于哪一类。

### 3.2 守卫清单

| # | 守卫 | 来源 | 观察什么 | 告知 | 终止 | 对应保证 | 参考来源 |
|---|---|---|---|---|---|---|---|
| 1 | 预算 | 核心，不可移除 | 步数、时长、token、费用、上下文的使用比例 | 剩余步数 ≤ max(1, 5%)；其余用到 90% | 步数、时长用完 → 收尾；token、费用用完 → 停止；上下文超出 → 在组装环节停止 | G1、G2 | context-budget |
| 2 | 内容过滤 | 核心 | finishReason | — | 停止 `content_filter` | G1 | sdk-finish-reason |
| 3 | 封路违规 | 核心 | 被封住的调用又被调用 | 不需要（封路时已经告知过） | 收尾，code 取封路时记下的原因 | G1 | — |
| 4 | **封路** | 标准 | 按 `tool+inputHash` 记录每个调用 | 满足下面任一条就封住并告知：确定性错误 1 次；有副作用且结果未知（超时、执行中抛错、结果没存下来）1 次；瞬时错误累计 2 次；连续 2 次结果相同（`repeatable` 的工具除外）；**有副作用的调用成功过一次**（`idempotent` 的工具除外） | 由守卫 3 处理 | G1、G2、安全 | signature-dead-loop、side-effect-ledger |
| 5 | 失败连击 | 标准 | 连续全部失败的步数；子运行失败计 2；任一调用成功就清零 | 2 | 3 → 收尾，主要是不可用错误时 code 为 `external_failure`，否则为 `failure_streak` | G1、G2 | failure-streak |
| 6 | 无新信息 | 标准 | 连续只得到重复结果的步数；成功执行的副作用算进展 | 3 | 8 → 收尾 `stall` | G1 | agent-engine 原有的 stall |
| 7 | 截断 | 标准 | 连续被截断（length）的次数 | 1，提示带具体策略 | 3 → 收尾 `truncated`，兜底要一份精简的结果 | G1 | length-truncation-streak |
| 8 | **静默推进（新增）** | 标准，可关闭 | 连续只调工具、没有文本的步数 | 5，要求先汇报进展 | 不终止 | 纠偏 | tool-only-loop |
| 9 | 计划推进 | 规划能力 | 计划建立后没有推进的步数 | 6 | 12 → 收尾 `no_progress` | G1 | agent-engine 原有的 progress |
| 10 | **顾问** | 标准，默认关闭 | 满足任一条就触发：收到纠偏后 2 步内问题仍在；每 5 步体检一次，发现异常（失败率超过 30%、平均文本不足 50 字、同一工具连续调用 3 次以上） | 调用模型做语义诊断，给出问题、建议，可以封路 | 不终止；每次运行最多 3 次 | 纠偏 | periodic + escalation |
| 11 | 业务守卫 | `task.guards`、`environment.guards` | 业务自己定 | 业务自己定 | 可以要求等待输入或终止 | 业务约束 | — |

计数类守卫（5、6、7、8、9）用 stdlib 提供的 `thresholdGuard` 声明：只写怎么计数、两个阈值、code 和提示文本；辅助函数保证每个周期到达终止前一定先告知过一次，并且同一周期内只告知一次。

### 3.3 引擎规则（四条，对修改封闭）

1. **先告知后终止**：一个守卫第一次要求终止之前，必须给出过告知；没有的话，本步先改成告知，下一步再终止。核心内置的守卫 1–3 不受这条约束。
2. **委托人引导就重来**：引导生效时，所有守卫重新 `start`，账全部清零，所有封路解除。
3. **出错时降级**：守卫出错或超时，视为没有意见；如果守卫声明了 `onError: 'stop'`，就按停止处理，code 为 `guard_error:<id>`。委托人联系不上时，守卫的"等待输入"改为收尾（同样先告知）。
4. **封路要有强制力**：工具流水线拦截被封住的调用；被封住的调用又被调用，由守卫 3 收尾。

### 3.4 裁决（core/decide.ts，纯函数）

- **合并前**：内容过滤 → 停止。
- **收集意见**，按来源顺序：核心内置 → 意图 → 候选（本步没有工具调用、只有文本，视为完成）→ 任务守卫 → 环境守卫 → 能力守卫 → 标准守卫。
- **合并顺序**：**停止 > 等待输入 > 完成 > 收尾 > 继续**。
  - 同一级别时，取来源顺序靠前的那条。
  - 多条告知合成一条纠偏消息；封住的调用取并集。
  - 守卫不能给出"完成"，也不能阻止完成。完成之后由交付验收把关。
  - "完成"排在"收尾"前面：模型已经给出了自己的交付，就先让它走交付验收，不强行改成兜底交付；验收不通过会被退回，下一步守卫照样会终止。
- **引导优先**：有已收到、还没生效的委托人引导时，完成、收尾、等待输入和意图工具的停止都改为继续，下一步带着引导重来（引擎和守卫的停止不让）。
- **合并后（预算）**：
  - 裁决为继续、但步数或时长用完 → 收尾；
  - 裁决为继续、但 token 或费用用完 → 停止；
  - 结构化交付下，收尾改为停止。

## 4. 纠偏：守卫的意见怎么让 agent 回到正轨

### 4.1 六种手段和分工

| 手段 | 由谁负责 | 例子 |
|---|---|---|
| 1. 去掉错误选项 | 封路（守卫 4）+ 工具流水线强制拦截 | 封住已经失败两次的调用、已经执行过的副作用调用 |
| 2. 在出错的地方说清楚 | 错误信封（由工具和流水线提供） | 参数错误时给出诊断；被封的调用返回封路原因和建议 |
| 3. 让模型自己复盘 | 纠偏消息 | 要求模型先用一两句话写明：已经确认了什么、还缺什么、下一步打算怎么做 |
| 4. 锚定目标 | 纠偏消息 | 带上任务目标和剩余预算 |
| 5. 给出口 | 纠偏消息 | 直接作答 / ask_user / report_blocked |
| 6. 换个视角 | 顾问（可选） | 语义诊断 |

### 4.2 纠偏消息（由核心统一渲染，集中在 `core/steering.ts`）

```
[纠偏 · 第 N 步]
目标：<任务目标>
发现：<problem>（<detail>）            ← 每个发出告知的守卫占一行；带封路的告知只写 problem
建议：<suggest>
已封住（再调用将收尾）：
- <工具>：<原因>；建议：<封路的建议>
剩余：步数 <x> / 时间 <y>
继续之前，请先用一两句话写明：已经确认了什么、还缺什么、下一步打算怎么做。
如果现有信息已经足够，直接给出结果；<委托人联系得上时：缺关键信息可以用 ask_user>；确实无法完成，用 report_blocked 说明原因。
```

- **每步最多一条**，总长不超过 2000 字。
- **位置**：放在工具结果之后，用 system 角色。厂商不支持在对话中间插入 system 消息时，改写为 user 内容里的 `[system]`（沿用现有做法）。
- **任务目标**：优先用任务新增的可选字段 `goal`；没有时取任务输入的开头 200 字。
- **出口**：根据本次运行实际可用的意图工具，以及委托人能否联系上来生成，不提供用不了的出口。
- **截断守卫的建议要写具体策略**：大段内容改用写文件的工具输出、精简推理过程、把任务拆开做。
- **同一件事只说一遍**：封路的原因和建议只在封路清单里出现，发现里不再重复。
- **建议按错误给**：参数错（`INVALID_INPUT`）就按错误信息修正参数，输入不同就不受封路影响；没有权限、委托人拒绝就不要重试；瞬时错误不要用相同输入重试，改用其他工具或基于已有信息作答；结果没有变化就基于已有结果决定下一步。失败连击同样按错误类别给建议。

### 4.3 被封住的调用返回什么

```
ERROR [TOOL_BLOCKED]: 该调用已被封住：<原因>（第 N 步）
HINT: <守卫的建议>。再调用将收尾
```

### 4.4 明确不做的事（Talor 的教训）

- 不用正则表达式判断模型的语义意图，再强制纠正它。
- 不在压力下强制模型收尾作答（Talor 的 forced-closure 导致模型自问自答）。
- 不发"你刚才错了"式的提示。
- 不每步重复同一条提示。

## 5. 交付环节（不变，只说明衔接）

- **完成与否只由交付环节判定**。守卫拦不住一次假完成，所以 `createEngine` 默认带上 completionReview：以拦截模式运行，最多退回 2 次，对应 Talor 的 judge-completion；交付物写 `checks: []` 可以关掉；groundingCheck 对应 Talor 的 quote-verifier；兜底交付 + sanitize 对应 Talor 的 forced-summary。
- **被退回时**，以 `source: delivery` 的纠偏消息回到下一步，守卫照常工作。

## 6. 效果保证

### 6.1 两条底线

| 底线 | 保证 | 怎么做到 |
|---|---|---|
| **收得住**：跑偏的运行一定会被收住 | 一定会结束 | 守卫 1–3；守卫 5、6、7、9 都有终止阈值 |
| | 终止前先告知 | 规则 1 |
| | 被封住的调用不会执行 | 规则 4 |
| | 副作用不会重复执行 | 封路的副作用触发条件 |
| **不误伤**：健康运行正常执行 | 健康运行零干预 | 守卫只在失败、没有新信息、截断、结果重复、长时间没有文本时才计数 |
| | 轮询类工具不被误封 | `repeatable` 豁免 |
| | 一步内并行失败不会被重罚 | 连击按步计数；封路按调用、并按错误类别计数 |
| | 模型的完成不被守卫打断 | 合并时完成排在收尾前面 |
| | 委托人引导后重新开始 | 规则 2 |

### 6.2 场景矩阵（都要写成测试）

| 场景 | 预期 |
|---|---|
| 同一调用出现瞬时错误 2 次 | 封住并告知；再调用 → 收尾 |
| 同一调用出现确定性错误 | 第 1 次就封住 |
| 不同调用连续失败 | 第 2 步告知"2/3，再失败将收尾"，第 3 步 → `failure_streak` |
| 失败和成功交替 | 不干预 |
| 一步内并行 3 个调用都失败，之后恢复 | 不干预 |
| 有副作用的调用成功后又被调用 | 被拦截，告知"已执行过" |
| 连续 5 步只调工具、没有文本 | 告知一次，要求汇报进展 |
| 健康的 20 步任务 | 零干预，`completed` |
| 轮询（repeatable，结果始终是 pending） | 不封路，由预算守卫兜底 |
| 说完"现在写入"就停手 | 被 completionReview 退回，接着把事做完 |
| 委托人引导 | 所有守卫清零，封路解除 |
| 子运行连续失败（每次计 2） | 先告知（规则 1 顺延），下一次失败再收尾 |
| 预算将尽 | 先告知，到点收尾，并有阶段性交付 |
| 守卫到了终止阈值，但模型这一步要完成 | 交给交付验收；被退回后下一步收尾 |
| 业务守卫出错（`onError: 'stop'`） | `stopped / guard_error:<id>` |
| 外部守卫没告知就要求终止 | 引擎改成告知，下一步再终止 |

### 6.3 验证手段

1. **单元测试**：每个守卫在告知和终止边界上的行为；错误分类；规则 1–4；新的合并顺序；纠偏消息的渲染。
2. **场景测试**：把 6.2 的矩阵加进 `scenarios.test.ts`。
3. **属性测试**：扩展 `invariants.property.test.ts`，随机生成运行，断言：一定结束；先告知后终止；健康运行零干预；被封住的调用从未执行；严格重放后裁决完全一致。
4. **回归重放**：比较新旧裁决，输出差异清单，逐条确认后再合入。
5. **一致性测试集**：新增 `conformance.guard`，检查四点：给同样的事实序列，得到同样的意见；意见的结构合法；不能冒充核心内置的硬终止；不能每一步都发出告知。

## 7. 探索实验：确定纠偏格式和阈值

| # | 要回答的问题 | 要对比的做法 |
|---|---|---|
| Q1 | 纠偏信息放在哪里最有效 | 只放在错误信封里 / 再加纠偏消息 / 两者都加 |
| Q2 | 纠偏消息写什么最有效 | 只写问题 / 问题 + 建议 / 再加目标、复盘、出口 |
| Q3 | 用什么角色 | system / user |
| Q4 | 封路什么时候封 | 按错误类别（当前方案）/ 一律第 2 次才封 |
| Q5 | 静默推进有没有必要、阈值多少 | 关闭 / 3 / 5 / 8 |
| Q6 | 顾问值不值得 | 关闭 / 开启 |
| Q7 | 不同模型差异多大 | 强模型、便宜模型、第三方模型 |

**场景套件**：用 fakeTool 构造确定性的跑偏场景，搭配真实模型来跑。

| 场景 | 模型应该怎么做 |
|---|---|
| 参数错误，可以修正 | 根据提示改参数 |
| 依赖不可用，有替代工具 | 换用替代工具 |
| 查询总是返回相同结果 | 换一种查询方式 |
| 缺少信息 | 用 search_tool 找工具，或用 ask_user |
| 说完"现在写入"就停手 | 被验收退回后接着做 |
| 委托失败 | 自己完成 |
| 有副作用的调用被重复调用 | 被拦截，不重复执行 |
| 轮询一个长任务 | 不被干预 |
| 健康的长任务 | 不被干预 |

**指标**：

| 指标 | 含义 |
|---|---|
| 任务成功率 | 交付通过验收 |
| 告知有效率 | 告知之后，问题在 2 步内消失 |
| 纠偏步数 | 从告知到回到正轨用了几步 |
| 误伤率 | 健康场景里出现干预的次数 |
| token 成本 | — |

**决策规则**：在成功率和最好的做法相差不到 5 个百分点的做法里，选最简单的那个。

**前提**：实验要调用真实模型，需要提供 API key，并定下要测的模型。

## 8. 架构

### 8.1 模块（高内聚：每个问题只由一个模块回答）

| 模块 | 职责 |
|---|---|
| `contracts/guard.ts` | `Guard`、`GuardOpinion`、`CallBlock` 的类型 |
| `core/facts.ts`、`core/error-class.ts` | 本步发生了什么；错误属于哪一类 |
| `core/decide.ts` | 核心内置守卫 1–3；合并顺序 |
| `core/steering.ts` | 纠偏消息和封路信封的渲染。纠偏格式只在这里改，也是实验的变量 |
| `executor/evaluate.ts` | 并行执行所有守卫；执行规则 1–3 |
| `stdlib/guards/threshold.ts` | 计数类守卫的辅助函数 |
| `stdlib/guards/{roadblock,standard,advisor}.ts` | 守卫 4–8 和 10 |
| `stdlib/capabilities/planning.ts` | 守卫 9 |
| `executor/deliver.ts` | 交付是否合格（不变） |

### 8.2 低耦合

- **守卫只能看到 `StepFacts` 和自己的账**，看不到 RunState，也看不到别的守卫。
- **守卫之间的冲突只由裁决解决**：靠来源顺序和合并顺序。
- **纠偏的措辞只在 `core/steering.ts` 里**，守卫只提供问题、建议和封住的调用。
- **依赖方向不变**，`eslint.config.js` 不用改。默认守卫仍然在 `index.ts` 里装配。
- **对外 API 统一**：原来的 `task.conditions`、`environment.rules`、能力返回的 `indicators`、引擎的 `supervision`，统一改为 `guards`。

### 8.3 扩展点与封闭点

| 扩展点 | 谁来扩展 | 约束 |
|---|---|---|
| 守卫 | 引擎默认、能力、执行环境、任务、应用 | 给同样的事实得到同样的意见；需要外部数据时通过 `ctx.record` 获取 |
| 错误分类 | 工具 | 只影响封路怎么计数 |
| 意图工具 | 能力 | 必须单独调用 |
| 交付验收 | 交付物、执行环境 | 唯一能拒绝完成的地方 |

**封闭、不开放的部分**：事实、错误分类表、守卫 1–3、规则 1–4、合并顺序、纠偏消息的结构。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 结局会有变化：瞬时错误晚一步收尾；模型的完成不再被守卫打断；默认不再做语义诊断 | 回归重放的差异清单逐条确认；需要语义诊断的场景打开顾问 |
| 防重复副作用误伤"有意重复"的操作 | 工具声明为 `idempotent` 就豁免；实验里专门覆盖这个场景 |
| 静默推进干扰正常的连续读取 | 阈值靠实验定，可以关闭 |
| 纠偏消息的效果因模型而异 | 措辞集中在 `core/steering.ts`，按实验结论调整 |
| 契约是破坏性改动 | 包还没发布，可以接受；旧日志通过 upcast 兼容 |
| 规则 1 顺延会让运行多走一步 | 最多多一步，并受预算守卫约束 |
